**Scrimsight Product Requirements Document**

**Version:** 2.0 (Revised)
**Date:** October 26, 2023
**Author:** Bard (based on provided source code and initial PRD)

**1. Introduction**

Scrimsight is a web application designed to provide in-depth analysis of Overwatch 2 scrims using log files generated by the "ScrimTime" workshop code (DKEEH).  It aims to be the go-to tool for Overwatch teams and players looking to improve their performance through data-driven insights. This document outlines the requirements for Scrimsight, covering its core features, target audience, technical specifications, and future roadmap.  This version significantly expands upon the initial draft, addressing key limitations and outlining a path towards a production-ready application.

**2. Goals**

*   **Comprehensive Analysis:** Provide a complete suite of tools for analyzing Overwatch scrim data, covering individual player performance, team compositions, match outcomes, and strategic trends.
*   **User-Friendly Interface:** Offer an intuitive and accessible user interface that is easy to navigate and understand, regardless of technical expertise.
*   **Actionable Insights:** Present data in a way that is easily interpretable and leads to actionable insights for coaches and players.
*   **Scalability and Performance:** Design the application to handle a large number of users, matches, and log files efficiently.
*   **Data Security and Privacy:** Ensure the security and privacy of user data through robust authentication, authorization, and data storage practices.
*   **Extensibility:** Build a flexible architecture that allows for easy addition of new features and integrations in the future.
*   **Community Engagement:** Foster a community around Scrimsight, encouraging user feedback and collaboration.

**3. Target Audience**

*   **Overwatch Coaches:**  Primary users, using Scrimsight to analyze team performance, identify weaknesses, and develop strategies.
*   **Competitive Overwatch Teams:**  Teams at all levels (amateur, collegiate, semi-pro, professional) using Scrimsight to track progress and gain a competitive edge.
*   **Individual Overwatch Players:**  Players seeking to improve their personal performance by analyzing their own gameplay data.
*   **Overwatch Analysts and Casters:**  Individuals who analyze and commentate on Overwatch matches, using Scrimsight to gain deeper insights.

**4. Release Criteria (MVP - Minimum Viable Product)**

The following criteria must be met for the initial release (MVP) of Scrimsight:

*   **Core Functionality:**
    *   User authentication and authorization (using a third-party provider like Firebase Authentication or Auth0).
    *   Secure file upload and parsing (with robust error handling).
    *   Data storage and retrieval (using a cloud-based database like Firebase Firestore or Supabase).
    *   Basic data visualization (charts and tables) for key metrics.
    *   Match, player, and team overview pages.
    *   Timeline visualization of match events.
*   **Performance:**
    *   The application should load and respond quickly, even with a moderate number of matches and players.
    *   Data processing should be efficient to minimize delays.
*   **Usability:**
    *   The user interface should be intuitive and easy to navigate.
    *   Key features should be easily discoverable.
    *   Basic user documentation should be available.
*   **Security:**
    *   User data should be securely stored and protected.
    *   Authentication should be handled securely.
*   **Testing:**
    *   Thorough unit and integration tests should be implemented.
    *   User acceptance testing (UAT) should be conducted with a small group of target users.
*   **Deployment:**
    *   The application should be deployed to a reliable hosting platform (e.g., Vercel, Netlify, AWS, Google Cloud).

**5. Features**

**5.1. User Account Management**

*   **Authentication:**
    *   User registration and login using a third-party authentication provider (e.g., Firebase Authentication, Auth0, or similar).  Discord OAuth is a good starting point, but consider others for broader appeal.
    *   Support for password reset and account recovery.
    *   Option for users to link their Discord account (for community features).
*   **Authorization:**
    *   Role-based access control (RBAC) with at least two roles:
        *   **User:** Can upload files, view data, and manage their own account.
        *   **Admin:** Can manage all users and data, configure application settings.
    *   Future:  Team roles (Coach, Player) with granular permissions.
*   **User Profile:**
    *   Users can view and edit their profile information (e.g., username, email, profile picture).
    *   Users can manage their linked accounts (e.g., Discord).
    *   Users can manage their subscription plan (future feature).

**5.2. File Management**

*   **File Upload:**
    *   Drag-and-drop file upload.
    *   File selection dialog.
    *   Support for multiple file uploads.
    *   Progress indicator for uploads.
    *   File type validation (only text files or `.txt` extension).
    *   File size limits (to prevent abuse).
    *   Error handling for failed uploads.
    *   **Asynchronous Upload:** Files should be uploaded in the background, allowing users to continue using the application.
*   **File Parsing:**
    *   Robust parsing of ScrimTime log files (DKEEH format).
    *   Error handling for invalid or corrupted log files.
    *   Detailed error messages to help users identify and fix issues with their log files.
    *   Support for different versions of the ScrimTime log format (if applicable).
    *   **Background Processing:** Parsing should happen in the background (e.g., using web workers or a serverless function) to avoid blocking the UI.
*   **File Storage:**
    *   **Persistent Storage:** Use a cloud-based database (e.g., Firebase Firestore, Supabase, AWS S3 + DynamoDB) to store parsed data.  *This is critical for a real application.*
    *   Data should be associated with the user's account.
    *   Implement data retention policies (e.g., delete data after a certain period of inactivity).
*   **File Listing:**
    *   Display a list of uploaded files, with file name, upload date, and match ID.
    *   Provide options to delete files.
    *   Implement pagination or infinite scrolling for large numbers of files.
*   **Sample Data:**
    *   Provide a set of sample log files for users to explore the application's features.
    *   Clearly indicate that sample data is being used.
    *   Allow users to easily switch between sample data and their own data.

**6. Data Model**

**6.1. Log Spec (Data Structure)**

The `LOG_SPEC` constant (in `src/atoms/files/scrimtime.ts`) defines the structure of the data extracted from the log files. This is a critical part of the application and should be well-documented and maintained.  The existing structure is well-defined and should be preserved.  Any changes to the log format generated by ScrimTime would require corresponding updates to this specification.

**6.2. Derived Data Structures**

The application derives several data structures from the parsed log data. These are well-defined using TypeScript interfaces and Jotai atoms.  Key structures include:

*   `MatchData`: Represents a single match.
*   `MapTimes`:  Start and end times for a match.
*   `RoundTimes`: Start and end times for each round.
*   `TeamStats`:  Aggregated statistics for a team.
*   `TeamPlayers`:  List of players for a team.
*   `TeamComposition`:  Hero composition and playtime.
*   `PlayerEvent`:  Individual player events (e.g., hero spawn, ability use).
*   `PlayerInteractionEvent`:  Events involving interactions between players (e.g., kills, damage, healing).
*   `UltimateEvent`:  Ultimate charge, start, and end events.
*   `GroupedKillOffensiveAssistEvent`:  Groups kills and assists occurring at the same time.
*   `PlayerStatsExpanded`:  Extends `PlayerStatLogEvent` with player role.
*   `PlayerLife`:  Tracks a player's life span within a match.
*   `PlayerMatch`:  Represents a player's participation in a match.
*   `Scrim`: Represents a set of matches between two teams.

**9. Open Questions and Considerations**

*   **Scalability:** The backend architecture must be designed to handle a large number of users, matches, and log files.  Cloud-based solutions like Firebase and Supabase are well-suited for this.
*   **Data Privacy:** User data must be stored and processed securely, complying with relevant privacy regulations (e.g., GDPR, CCPA).  Clear privacy policies and data handling procedures are essential.
