Objective: Implement a V2DataFlow page using best practices and in the same style as the other pages. It is a dashboard that displays the following information in an organized manner emphasizing visual hierarchy: 

Observability Points:

Here's a breakdown by layer and concern:

1. Raw Layer (rawAtoms.ts, File Input):

    File Loading:

        Metric: Number of files successfully loaded vs. attempted.

        Metric: Time taken to read file content (readFileAsync).

        Log/Trace: Errors during readFileAsync.

        Log: Names and sizes of loaded files.

        Metric/Log: Whether sample data is being used (sampleDataAtom).

    Input State:

        Observe: Value of rawLogInputAtom (number of files).

        Observe: Value of rawLogContentAtom (number of RawLogContent objects, total content size in bytes/lines).

2. Bronze Layer (bronzeAtoms.ts, bronzeLogic.ts, bronzeSchema.ts):

    Parsing & Validation Pipeline (processRawLogsToBronze):

        Metric: Total number of raw log lines processed.

        Metric: Time taken to process all raw logs into Bronze data.

        Metric: Number of lines successfully parsed (parseLogLine returning non-null).

        Metric: Number of lines failing parsing (parseLogLine returning null).

        Log/Trace: Log lines that failed parsing (Error parsing log line: in parseLogLine).

        Metric: Frequency of warnings for missing eventSpec in parseLogLine.

        Metric: Frequency of warnings for missing fieldSpec in parseLogLine.

        Metric: Frequency of timestamp parsing errors (Error parsing timestamp: in parseTimestampString).

        Metric: Number of events successfully validated by Zod (validationResult.success).

        Metric: Number of events failing Zod validation.

        Log/Trace: Zod validation errors (validationResult.error), including the specific event type and error details (Validation failed for event type:).

        Metric: Frequency of warnings for missing Zod schemas (Schema not found for event type:).

        Metric: Number of events generated per eventType.

        Metric: Time taken for generateMatchId.

    State (bronzeParsedEventsAtom):

        Observe: Size and structure of the data held by bronzeParsedEventsAtom (e.g., number of keys/event types, number of events per type).

        Metric: Computation time of bronzeParsedEventsAtom.

3. Silver Layer (silverAtoms.ts, silverLogic.ts, silverSchema.ts):

    Transformation Logic (calculateSilver* functions):

        Metric: Time taken for each calculateSilver* function (e.g., calculateSilverMatches, calculateSilverPlaytime, calculateSilverTeamfights).

        Metric: Number of input Bronze events processed by each function.

        Metric: Number of Silver entities generated by each function (e.g., number of matches, rounds, teamfights, player lives).

        Log/Trace: Errors or unexpected conditions within the calculation logic (e.g., failure to find corresponding start/end events, issues in teamfight grouping logic, errors in getRoundNumberForTime).

        Metric: Consistency checks (e.g., does total calculated playtime match round duration? Do teamfight kills align with overall kills?).

        Metric: Number of calls to uuidv4 (can indicate volume).

    State (silver*Atoms):

        Observe: Size of the arrays held by each Silver atom (e.g., silverMatchesAtom, silverPlayerRoundStatsAtom).

        Metric: Computation time of each Silver atom.

        Observe: Dependencies between Silver atoms (e.g., knowing silverPlayerRoundStatsAtom depends on silverPlaytimeAtom helps trace issues).

4. Gold Layer (goldAtoms.ts, goldLogic.ts, metricsSchema.ts, metricsConfig.ts):

    Aggregation Engine (getAggregatedMetricsAtom, calculateAggregatedMetrics):

        Metric: Number of times getAggregatedMetricsAtom is computed for new parameter sets (cache misses). Monitor the parameters (AggregationParams) requested.

        Metric: Computation time for getAggregatedMetricsAtom instances.

        Log/Trace: Errors finding the sourceAtom (Source atom ${params.sourceAtom} not found).

        Metric: Size of sourceData input to calculateAggregatedMetrics.

        Metric: Time taken by calculateAggregatedMetrics.

        Metric: Number of rows before and after filtering in calculateAggregatedMetrics.

        Metric: Time taken specifically by the pandas-js groupBy().agg() operation.

        Log/Trace: Errors during pandas-js operations (Error during pandas groupBy/aggregation:).

        Metric: Size of the groupedDf collection.

        Metric: Time taken for post-aggregation calculations (ratio, per10min, derived).

        Log/Trace: Errors during post-processing (Error post-processing aggregated data:).

        Metric: Number of NaN/Infinity values cleaned up.

        Metric: Final number of rows in the aggregated result.

    Metric Dependencies (resolveMetricDependencies):

        Metric: Time taken by resolveMetricDependencies.

        Log: Input metricIds and the resulting resolvedMetrics list (useful for debugging dependency issues).

    State & Configuration:

        Observe: The parameters (AggregationParams) passed to getAggregatedMetricsAtom.

        Observe: The resolved metricsConfig used in calculations.

5. General / Cross-Cutting Concerns:

    Performance:

        End-to-end processing time (from file load to Gold metrics availability).

        Memory usage, especially the size of data held in Jotai atoms at each layer.

        CPU usage during intensive calculations (Bronze parsing, Silver transformations, Gold aggregation).

    Error Handling:

        Centralized logging of all caught errors and warnings across all layers.

        Rate of specific errors (e.g., Zod failures, parsing errors, pandas errors).

    Transparency:

        Ability to inspect the data at each layer boundary (Raw input -> Bronze events -> Silver entities -> Gold aggregates). This is inherent in the Jotai atom structure but needs tooling/UI to expose.

        Logging the parameters used for Gold layer aggregations alongside the results.

        Clear logging of which files contributed to which match IDs.

Summary of High-Priority Monitoring:

    Bronze Layer Validation: Monitor Zod validation failures (bronzeLogic.ts). This indicates input data quality issues.

    Layer Transition Times: Measure the time taken for each major transformation step (Raw->Bronze, Bronze->Silver atoms, Silver->Gold atoms). Identifies bottlenecks.

    Gold Aggregation Performance: Monitor the time taken by calculateAggregatedMetrics and specifically the pandas-js operations.

    Gold Atom Cache Efficiency: Monitor how often getAggregatedMetricsAtom recalculates for the same effective parameters (indicates issues with the custom comparator or unnecessary re-renders).

    Error Rates: Track the frequency of parsing errors, validation errors, and calculation errors across all layers.

    Data Volume: Monitor the number of events/entities at each layer (e.g., Bronze events per type, Silver matches/rounds/teamfights, Gold result rows). Helps understand performance characteristics.
